# 订单服务超时故障复盘

## 1. 故障概述

2026 年 3 月，用户服务调用订单服务时出现间歇性超时。

随着请求量增加，订单服务的连接池逐渐耗尽，最终影响正常业务请求。

这是一次由超时控制不合理和重试策略不当共同引发的故障。

## 2. 故障现象

故障期间出现了以下现象：

- 用户服务调用订单服务时频繁发生 HTTP 超时。
- 下游订单服务响应时间持续增加。
- 用户服务在下游响应变慢时进行了多次重试。
- 重试请求进一步增加了订单服务的负载。
- 订单服务连接池最终耗尽。

## 3. 根因分析

### 3.1 没有合理设置总超时时间

用户服务虽然发起了 HTTP 请求，但没有设置合理的业务调用链路总超时时间。

请求可能在多次调用和重试过程中持续占用资源。

### 3.2 重试放大故障

当订单服务响应变慢时，用户服务继续发起重试。

这些重试请求增加了订单服务的负载，使得原本已经变慢的服务承受了更大压力。

### 3.3 连接池耗尽

大量请求和重试进一步消耗了订单服务的连接池资源。

连接池耗尽后，正常请求也难以获得可用连接，导致故障范围扩大。

## 4. 故障处理措施

本次故障采取了以下修复措施：

1. 为 HTTP 请求设置明确的超时时间。
2. 为整个业务调用链路设置总超时时间。
3. 限制最大重试次数，默认最多重试 2 次。
4. 为非幂等请求增加幂等保护。
5. 增加连接池使用率和请求延迟监控。
6. 在下游持续异常时启用熔断机制。

## 5. 经验总结

这次故障说明，超时、重试和连接池管理不是彼此独立的问题。

如果只增加重试次数，而没有合理的超时和熔断控制，重试可能从故障恢复手段变成故障放大器。

服务调用必须同时考虑：

- 单次请求超时。
- 业务调用链路总超时。
- 最大重试次数。
- 幂等性保护。
- 熔断机制。
- 连接池资源使用情况。
